# yebeyt server

The backend at **api.yebeyt.com** (Railway): Hono, Postgres with Drizzle, Zod. The HTTP contract is `packages/api/openapi.json`, written from the code (see "The contract").

Sign-in is Apple or Google only. The server keeps the provider's account id, the verified email the provider gives (to link Apple and Google with one email into one account, and to write to the person; never logged), the choice to get news by email (off by default), the username and an optional display name (the name the person chose to show; it is never read from the provider's token), and nothing else about the person: no IP. Logs are one line per request (method, route pattern, status, ms).

## Commands

Run from the repo root (Node 22 or newer, pnpm 12):

```bash
pnpm install
pnpm -r typecheck
pnpm -r test                                   # vitest; Postgres runs in-process (PGlite), no network
pnpm --filter @yebeyt/server api:check         # fails when packages/api/openapi.json is stale
pnpm --filter @yebeyt/server api:generate      # rewrites it; commit the result
pnpm --filter @yebeyt/server build             # tsc → apps/server/dist
pnpm --filter @yebeyt/server db:generate       # after editing src/db/schema.ts: writes a migration into drizzle/ (commit it)
```

Migrations in `drizzle/` are applied every time the server starts.

## Environment

All are checked at start; a missing or malformed one stops the server with a message naming the variable (never its value).

| Variable | What |
|---|---|
| `DATABASE_URL` | `postgres://…` (Railway's Postgres plugin provides it) |
| `JWT_SECRET` | 32+ random characters. Signs access tokens (HS256); the key that seals the stored Apple refresh tokens is derived from it. Changing it signs everyone out and makes stored Apple tokens unreadable (account deletion then skips the Apple revoke for them) |
| `APPLE_BUNDLE_IDS` | comma list of accepted audiences, e.g. `com.yebeyt.app` |
| `APPLE_REDIRECT_URIS` | optional comma list of the return URLs a web client may name for Sign in with Apple JS, e.g. `https://app.yebeyt.com/auth/apple` (Apple wants it again at the code exchange); the web Services ID goes in `APPLE_BUNDLE_IDS` |
| `APPLE_TEAM_ID`, `APPLE_KEY_ID` | for the client-secret JWT sent to Apple (code exchange and revoke) |
| `APPLE_PRIVATE_KEY` | the `.p8` PEM; `\n` escapes are accepted so it fits on one line |
| `GOOGLE_CLIENT_IDS` | comma list of accepted OAuth client ids (the iOS one, later the web one) |
| `ADMIN_TOKEN` | 16+ random characters; the Bearer token for `/v1/admin/*` |
| `PORT` | default 8080 (Railway sets it) |

## Local development

The tests need nothing installed. To run the server itself you need a Postgres (any 14+) and a `DATABASE_URL`:

```bash
createdb yebeyt
export DATABASE_URL=postgres://localhost/yebeyt JWT_SECRET=$(openssl rand -hex 32) \
  APPLE_BUNDLE_IDS=com.yebeyt.app APPLE_TEAM_ID=TEAMID1234 APPLE_KEY_ID=KEYID12345 \
  APPLE_PRIVATE_KEY="$(awk 'NF{printf "%s\\n",$0}' AuthKey_XXXX.p8)" \
  GOOGLE_CLIENT_IDS=x.apps.googleusercontent.com ADMIN_TOKEN=$(openssl rand -hex 16)
pnpm --filter @yebeyt/server dev        # tsx watch on :8080
curl localhost:8080/health
```

Without a local Postgres, PGlite can stand in as a server: `npm i @electric-sql/pglite @electric-sql/pglite-socket` in a scratch folder, start `new PGLiteSocketServer({ db: await PGlite.create(), port: 54329 })` and use `DATABASE_URL=postgres://postgres:postgres@127.0.0.1:54329/postgres`. (Real Apple/Google sign-in needs real tokens and the real keys; the tests use locally generated ones.)

## Endpoints

`/health`, `/v1/auth/{apple,google,refresh,logout}`, `/v1/me` (GET, DELETE), `/v1/me/profile`, `/v1/me/username`, `/v1/me/avatar`, `/v1/me/progress`, `/v1/me/divan` (merge-sync of kept couplets), `/v1/me/privacy`, `/v1/me/friends`, `/v1/me/friend-requests`, `/v1/me/stats`, `/v1/friend-requests/{username}` (+ `/accept`, `/reject`), `/v1/friends/{username}`, `/v1/users/{username}`, `/v1/users/search`, `/v1/scores`, `/v1/daily`, `/v1/daily/{date}/friends`, `/v1/leaderboard/{league,friends,global}`, `/v1/reactions/{kind}`, `/v1/reactions/counts`, `/v1/me/reactions`, `/v1/feed`, `/v1/usernames/{check,suggestions}`, `/v1/poets/pictures`, `/v1/poets/{slug}/picture`, `/v1/admin/poets/{slug}/picture`, `/v1/feedback` (+ `/{id}/screenshot`, `/{id}/recording`), `/v1/admin/feedback` (+ `/{id}/screenshot`, `/{id}/recording`), `/v1/blocks/{username}`, `/v1/me/blocks`, `/v1/reports`, `/v1/admin/reports`, `/v1/conversations` (+ `/{id}/messages`, `/{id}/read`), `/v1/messages/{id}`, `/v1/me/unread`, `/v1/shared-divans` (+ `/{id}/items`, `/{id}/items/{itemId}`, `/{id}/items/{itemId}/like`), `/v1/games` (+ `/{id}`, `/{id}/join`, `/{id}/moves`, `/{id}/resign`, `/by-code/{code}/join`), `/v1/me/games`, `/v1/challenges` (+ `/{code}`, `/{code}/results`), `/v1/me/challenges`, `/v1/public/users/{username}`, `/v1/public/games/{code}`, and the WebSocket `/v1/live` (not in the contract; see "Messages" and "Playing with friends"). Details, bodies and error codes are in `packages/api/openapi.json`. Errors are `{ "error": "<code>" }` (e.g. `username_taken`, `username_change_too_soon` with `allowedAt`); the apps turn codes into Persian copy.

Sessions: access token = JWT, 15 minutes; refresh token = random 32 bytes, stored as a sha256, 60 days, single use (rotated on every refresh). Showing a used refresh token again revokes that whole sign-in, unless it was used less than 10 seconds ago (a client retrying or racing itself): then that call is just refused (401) and the sign-in stays. Apple sign-in requires the raw `nonce` (the identity token must carry its sha256). JSON bodies are limited to 64 KB; the divan sync to 1 MB (2000 items); the admin picture upload to 15 MB. A user can keep at most 20 000 divan rows (kept or removed); past that a PUT that adds new keys gets 413 `divan_full` (a soft limit: two parallel requests can go slightly over).

## Feedback

`POST /v1/feedback` takes a report of one of five types (`bug`, `annoyed`, `idea`, `game`, `liked`); sign-in is optional (a token that is sent must be valid, else 401). The fields allowed per type are in the contract (e.g. `technical` only on bug, `screen` only on bug and annoyed, a `game` idea only on game); the body is limited to 32 KB and unknown keys, also inside `technical`, are refused. App version, phone model and OS version are required on every type. The server stores the text and these fields, the user id when signed in, and nothing about the connection: no IP, location or device id (logs hold only method, route, status, ms). The answer carries an `uploadToken` (random 32 bytes, only its sha256 is stored) valid 15 minutes for `PUT /v1/feedback/{id}/screenshot` (JPEG or PNG, 3 MB; bug, annoyed, idea) and `/recording` (MP4, 25 MB; bug), sent as `X-Upload-Token`. The first bytes must match the declared type (PNG, JPEG, MP4), else 415. One file per kind (a second gets 409 `already_uploaded`). Attachment budget per hour, in memory: 200 MB per signed-in user and 500 MB for all guests' reports together (429 `rate_limited`; only stored files are charged, refused uploads cost nothing); at most 3 uploads are handled at once, the rest get 503 `busy` with `Retry-After`; a file that takes over 60 seconds to arrive gets 408 `upload_timeout`. Files are stored in Postgres (`feedback_attachments`, bytea) for now; moving them to object storage is later work.

Rate limits, in memory (they restart with the server): 10 reports an hour per signed-in user; all guests together share 120 an hour (429 `rate_limited`).

`GET /v1/admin/feedback?type=&before=` (admin token) lists newest first, 50 a page, with the username when there is one and each attachment's kind and size; `nextBefore` is the cursor for the next page. `GET /v1/admin/feedback/{id}/screenshot|recording` downloads the file as an attachment. Deleting an account keeps its reports as anonymous feedback (`user_id` becomes null); the attachments stay too.

## Friends, scores and leagues

Every endpoint of this part needs a signed-in user. Bodies are limited to 64 KB, logs hold only method, route pattern, status and ms (never a username, key or id).

**Friend requests and friends.** People are not followed: friendship needs a request and its acceptance (`friend_requests` `from_id`→`to_id`; `friendships` with `user_low` < `user_high`). All of these (the lists too) need a signed-in user with a username (403 `username_required`); yourself is 400, an unknown username 404, and if either of the two blocked the other the person is 404 too. `POST /v1/friend-requests/{username}` sends a request (200 `{friendship}`; idempotent; when they already asked me it accepts and we are friends; when we are friends it does nothing). It counts against 30 **new** requests an hour per user (429 `rate_limited`; repeats and acceptances do not count; in memory). `DELETE /v1/friend-requests/{username}` cancels mine (204). `POST /v1/friend-requests/{username}/accept` accepts theirs (200; 404 when they sent none; 200 when already friends) and `.../reject` throws it away (204): **silent**, the sender is not told, the request just disappears, and they may send a new one at once. `DELETE /v1/friends/{username}` unfriends, silent (204); either may ask again. `GET /v1/me/friends` and `GET /v1/me/friend-requests?direction=incoming|outgoing` are paged, 50 a page, newest first, with an opaque `cursor` (`nextCursor` is null on the last page) and give `{username, displayName, avatar}` (requests add `createdAt`; the friends list and each search result below add `canPlay`: whether the person can be invited to a game; when false an invitation is skipped as `not_found`, so clients leave them out of invite pickers; today only the demo friend «یه بیت»). `GET /v1/users/{username}` is the public profile (`friendship`: `none`, `requested` (I sent), `incoming` (they sent) or `friends`; `isFriend` is `friendship == friends`; `canMessage`: may I write to them now, by the same rule as sending; `friendsCount`, `league: {tier} | null` and `weekPoints`, both null unless the person is a friend, yourself, or allows the global leaderboard; `league` is also null before their first score of the week). `GET /v1/users/search?q=` is a case-insensitive prefix match on the username (at least 2 characters, at most 20 results, never the caller; each with `friendship` and `isFriend`; 60 searches a minute per user). `search` is a reserved username so it can never clash with a profile. Friend-request writes, reactions and scores are limited to 120 a minute per user (in memory, 429 `rate_limited`). `GET /v1/me/unread` gives `{total, friendRequests}`: the unread messages and the incoming requests, for the tab badge. Everywhere that used to mean mutual follows (the feed, the friends leaderboard, daily results, shared divans, game invitations, «بهم پیام بده») now means friendships. The built-in demo friend «یه بیت» (`yebeyt`, the user flagged `users.is_house`) accepts a request at once, through the same lock and friendship code as an accept; its `friendsCount` shows 0 and it never appears in leaderboards, leagues, the feed or daily results.

**Scores.** The phone reports each finished round with `POST /v1/scores {roundId, game, points, playedAt}`. `roundId` (a uuid the phone makes) is the row's id, so sending it again changes nothing and answers the stored result; another user's round id is 409 `conflict`. `daily` counts once per user per Tehran day (of `playedAt`) and `onboarding` once per user ever; a second one with a new `roundId` is 409 `conflict`. `points` over the game's cap is 400 `points_too_high` (daily 100, jigsaw 320, poet / second / book 440, match 50, listen 100, onboarding 50). `playedAt` must be within the last 48 hours and at most 5 minutes ahead (400 `bad_timestamp`). A round counts for the Tehran week **the server receives it in**, so a week that has closed never changes. `POST /v1/daily {date, solved, tries}` stores the daily puzzle's result for a Tehran day, first write wins (a day from 48 hours ago up to today). `GET /v1/daily/{date}/friends` lists friends' results (solved first, then fewer tries; up to 100) with `solvedCount`; a friend whose `dailyVisibility` is `me` is left out. `GET /v1/me/stats` gives `totalPoints`, `weekPoints`, `streakDays` (days in a row the daily puzzle was solved, ending today or yesterday, by Tehran date) and the league tier.

**Weeks.** A week runs Saturday 00:00 to Friday 24:00 in Tehran (fixed UTC+03:30; no daylight saving since 2022). Its id is the ISO week id (`2026-W47`) of the same week moved two days later (Saturday plays Monday), so the ids sort as text and 2026 has a week 53 (`src/week.ts`).

**Leagues.** The first score of a week puts the user in a league group (`league_groups`, `league_members`): a group of the same week and tier with fewer than 30 members, made when none has room. The tier is the one the user earned in the last week they played (`user_tiers`; no row means tier 0 نوآموز; the other tiers are بیت‌خوان, غزل‌باز, سخن‌دان, استاد سخن, 0 to 4). Joining takes a Postgres advisory lock per week and tier, in the same transaction as the score, so two joins cannot fill the same place; a user has at most one group a week. When a week ends, `closeWeek(db, week, at)` ranks each group by points, then the earlier last score (the time the server got it), then user id: the top 5 move up a tier and the bottom 5 of the rest move down (tiers stay within 0 to 4; in a group of 10 or fewer nobody is both), the others stay. Weeks are closed lazily: the first request of a new week to `/v1/scores`, `/v1/me/stats`, `/v1/leaderboard/*` or `/v1/users/*` closes every earlier week that has groups and no row in `league_closures`, oldest first, under an advisory lock (so another instance, or a repeat, does nothing). A user who skips a week keeps their tier. `GET /v1/leaderboard/league` gives `{week, tier, endsAt, rows, promoteCount: 5, demoteCount: 5}` (rows are empty until the user's first score of the week; a stranger in the group who keeps off the global list comes as `hidden: true` with no username, name or picture, for the app to show «یه نفر», but with real points and rank; friends and people on the global list show normally); `/v1/leaderboard/friends` ranks me and my friends by this week's points (friends with none show 0; up to 100); `/v1/leaderboard/global?cursor=` ranks everyone with `inGlobalLeaderboard` on who scored this week (50 a page), plus `me`, the caller's own rank among them even when the caller is hidden. All standings are SQL aggregates over `score_events` (indexes on `(user_id, week)` and `(week, user_id, points)`), with no per-row queries.

**Likes, reposts and the feed.** `PUT/DELETE /v1/reactions/{like|repost}?key=<couplet key>` (the key is a query parameter, `#` percent-encoded; no body) is idempotent and answers that couplet's counts. `GET /v1/reactions/counts?keys=a,b` (up to 50 keys, `#` percent-encoded) gives `{key: {likes, reposts, likedByMe, repostedByMe}}` for everyone's reactions. `GET /v1/me/reactions?cursor=` lists my own likes and reposts as `{key, kind, at}`, newest first, 200 a page (`nextCursor` is null on the last page); the phone pulls them when it signs in. `GET /v1/feed?cursor=` is the home «دوستات» feed: newest first, 30 a page, from friends only: their likes and reposts when their `keptVisibility` is `friends` (the switch that also hides their divan), and their **solved** daily puzzles when `dailyVisibility` is `friends`. Items are `{type: "like"|"repost"|"daily", user, key?, date?, tries?, at}`. It is one `UNION ALL` of the two tables on the `(user_id, created_at)` indexes.

Deleting an account (`DELETE /v1/me`) removes its friendships and friend requests (both ways), scores, daily results, league places, tier and reactions; league groups it was in stay for the others.

## Messages, live updates, shared divan, block and report

Every endpoint here needs a signed-in user with a username (403 `username_required` otherwise). Errors, bodies and limits are in `packages/api/openapi.json`; this is what the contract cannot say.

**Blocks and reports.** `PUT/DELETE /v1/blocks/{username}` (idempotent, 204) and `GET /v1/me/blocks`. Blocking removes the friendship and the friend requests between the two, and they come back only if they ask and accept again after unblocking. A blocked pair, whoever blocked, cannot send a friend request (404), open a chat, send, or share a divan, and is hidden from each other: profile lookup is 404, search leaves them out, and their chat and shared divans are left out of the lists and answer 404; sending into an existing chat is 403 `messages_closed`. Nobody is told. `POST /v1/reports {username, messageId?, reason: spam|abuse|other, note?}` (10 a minute; a `messageId` must be a message of that person in a chat the reporter is in); `GET /v1/admin/reports?before=` (admin token) lists newest first, 50 a page, with the reported message's content when there is one. A report keeps a copy of the reported message (kind, text, key, note) taken when it is filed, so it can still be read if the sender deletes the message (`deleted: true`). A report stays when either account is deleted (the reporter or the target then shows as null).

**Chats.** One chat per pair (`conversations`, `user_low` < `user_high`). `POST /v1/conversations {username}` gets or makes it when the other person's `messagesFrom` is `all`, or `friends` and we are friends, or that person already wrote in our chat; else 403 `messages_closed`. `GET /v1/conversations` lists chats that have at least one message, newest message first, 50 a page, with `other` (`canPlay`, as in the friends list, here and in the chat `POST /v1/conversations` opens; `online` is null unless that person's `showOnline` is on), `last` (kind, text, couplet `key`, `note`, `deleted`, `at`, `fromMe`, `event` (the `payload.event` of a system or game line, else null): the server holds no poem text, so the app renders a couplet from its key) and `unread`. `GET /v1/me/unread` is the total for the tab badge. Unread counts the other person's messages (text, couplet and game lines) after the last one marked read; system lines and deleted messages do not count.

**Messages.** `GET /v1/conversations/{id}/messages?before=&limit=` (newest first, at most 50, `nextBefore`, and `otherReadMessageId` for «دیده شد»). `POST` sends `{clientId, kind: "text", text}` (1 to 1000 characters) or `{clientId, kind: "couplet", key, note?}` (note up to 200); `clientId` makes it idempotent per sender (a repeat is 200 with the first message, a new one 201); blocks and `messagesFrom` are checked again on every send, except that answering a person who has already written in the chat is allowed whatever their `messagesFrom` says (a block still stops it); 30 a minute per user. `PUT /v1/conversations/{id}/read {messageId}` moves the read mark forward only (the update itself refuses to go back, so parallel calls cannot). `DELETE /v1/messages/{id}` (sender only; 403 for anyone else and for system lines) keeps the row as `deleted` and clears its text, key, note and payload, and both people get a live `deleted` event. Messages have `kind` `text`, `couplet`, `system` or `game`; a system or game line carries `payload: {event, ...}` (`divan_add` has `key`). Game messages (`kind: "game"`) are the invitations of `POST /v1/games` (payload `{event: "game_invite", gameId, kind, code}`) and the results of challenges (`{event: "challenge_result", code, game, score, seconds}`); see "Playing with friends". A message to «یه بیت» gets one couplet back (kind `couplet`, one of 30 well-known keys of the game deck in `src/house.ts`, never the same as its last reply in that chat) after 1–2 seconds, through the normal message path (live event, unread count); at most one reply per 2 seconds and 30 a day per person (kept in memory), silence beyond that and while either has blocked the other; a failed reply is logged and dropped.

**Shared divans.** Between two friends: `POST /v1/shared-divans {username}` gets or makes it (403 `forbidden` when not friends), `GET /v1/shared-divans` lists them with `counts: {total, mine, theirs}`, `GET /v1/shared-divans/{id}/items?by=me|them|all&cursor=` pages the couplets (50, newest first; `counts` cover the whole divan whatever `by` says). `POST .../items {key, note?}` adds one (403 `forbidden` once we are no longer friends; a couplet that is already there answers 200 with the item and does nothing else), puts a system line `{event: "divan_add", key}` in our chat (made if needed, whatever `messagesFrom` says), and sends live events. `DELETE .../items/{itemId}` is for whoever added it; `PUT/DELETE .../items/{itemId}/like` is each person's own like (the item shows `likedByMe` and `likedByThem`). An existing divan stays readable if the two stop being friends.

**Live: `wss://api.yebeyt.com/v1/live`.** A WebSocket (`@hono/node-ws` on the `@hono/node-server` server, `src/live.ts`, `src/server.ts`). The first message must be `{"type":"auth","token":"<access token>"}` within 5 seconds; the server answers `{"type":"ready"}`. Otherwise it closes with code 4401 (bad token, anything else first, or no message in time) or 4403 (no username yet). The socket lives as long as its access token: when the token expires (15 minutes) the server closes it with 4401 and the client reconnects with a fresh token. A frame over 4 KB closes the socket (1009). A user may have 5 sockets; a sixth closes the oldest with 4409. Events (JSON text frames):

- `{type:"message", message}`: a new message, as in the message list (`fromMe` is for the receiver; both people get it, so a second phone of the sender sees it too).
- `{type:"read", conversationId, username, messageId}`: the other person (`username`) read up to that message; sent only when their mark moved forward.
- `{type:"deleted", conversationId, messageId}`: the sender deleted a message (both people get it).
- `{type:"presence", username, online}`: only to people who share a chat that has a message with that person and are not blocked, and only if the person's `showOnline` is on. Online means at least one authenticated socket. When a connected person turns `showOnline` off, their watchers get an offline event; turning it back on sends online.
- `{type:"divan", sharedDivanId, item}`: a couplet was added to a shared divan (`item` as in the items list).
- `{type:"divan.removed", sharedDivanId, itemId}`: the person who added a couplet took it out of the shared divan (both people get it; the chat line «… اضافه کرد» stays).
- `{type:"friend.request", from: {username, displayName, avatar}}`: to the receiver of a new friend request; `{type:"friend.accepted", from: {username, displayName, avatar}}`: to the sender when `from` accepts (or sends back a request at once). Nothing is sent when a request is rejected, cancelled or a friend removed.
- Games and challenges: `game.started`, `game.move`, `game.turn`, `game.ended`, `duel.question`, `duel.answered`, `duel.round`, `challenge.result`, and the one message a client sends, `duel.answer` (see "Playing with friends").

The server pings every 25 seconds and drops a socket that has not answered the previous ping. Events for a user with no open socket are not kept: the app reads the lists on opening. The hub (`src/hub.ts`) is **in memory, so this works for one server instance only**: with more than one, an event made on one instance would not reach sockets on another. Scaling out needs the events to go through Postgres LISTEN/NOTIFY or Redis pub/sub (and presence kept there too). Push notifications wait for an APNs key.

Deleting an account (`DELETE /v1/me`) also removes its games (a waiting game goes; an active game ends with the other player as winner, who keeps the finished game), its challenges with all their results and its results on other people's challenges, its blocks, read marks and likes, **every chat it was in with all their messages (the other person loses that chat)** and every shared divan with its couplets and likes. Reports it filed or that name it stay, with the reporter or the target set to null.

## Playing with friends

Every endpoint here needs a signed-in user with a username, except looking up a challenge and leaving a result on one (a person without an account may do both). Bodies, limits and error codes are in `packages/api/openapi.json`; this is what the contract cannot say. The product rules are in `docs/yebeyt-2.md` («Playing with friends, decisions for slice 7c»).

**Games.** `POST /v1/games {kind: "mosh"|"duel", turnSeconds?, invite: [username ≤ 5]}` makes a game that waits for a second player, with a four-character `code` (Crockford base32 without I, L, O, U; read in any case, O as 0, I and L as 1). مشاعره needs `turnSeconds` 30, 120 or 86400; رودررو is 8 (or left out). Each invitee gets a chat message of kind `game` with payload `{event: "game_invite", gameId, kind, code}` (a chat is made if there is none, whatever their `messagesFrom` says); a person who blocked you or whom you blocked, or who does not exist, or is the demo friend «یه بیت» (`not_found`: a block is never told), or who takes game invitations only from friends when you are not one (`friends_only`), is skipped and named in `skipped`. `POST /v1/games/{id}/join` or `POST /v1/games/by-code/{code}/join` (20 a minute per user; only for a game that is not done, so a done game's code is free again and codes are unique only among open games): the first to join takes seat 1 and the game is active («هر کی اول اومد»); the others get 409 `game_full`; joining a game you are in is 200. `GET /v1/games/{id}` (players only) and `GET /v1/me/games` (waiting and active games, and games finished in the last 7 days; 50 at most). 20 new games an hour per user. When a game ends the winner is stored, a system line `{event: "game_ended", gameId, kind, reason, by: <winner>}` goes in the chat of the two (`reason`: `timeout`, `resigned`, `left`, `finished`; a game nobody joined for 7 days ends as `expired` with no line), both get a live `game.ended`, and the league gets `mosh` or `duel` score events (below). Finished games are kept; a deleted account's player rows go with it.

**مشاعره.** The creator opens (seat 0) with any couplet; the turns alternate. `POST /v1/games/{id}/moves {key, m1, m2}`: it must be my turn and within the deadline (the last move's time, or the time the game became active, plus `turnSeconds`); a request after the deadline ends the game with the other as winner and answers 409 `turn_over`. The first letter of `m1` must be the last letter of the previous couplet's `m2` (409 `wrong_letter`), compared with diacritics, punctuation, digits, half-spaces and a lone hamza skipped, and آ read as ا, ي and ى as ی, ك as ک, أ and إ as ا, ۀ and ة as ه, ئ as ی (`src/persian.ts`, tested with a table). A couplet may be played once per game, by key (409 `already_played`). The server checks the couplet against Ganjoor (below): the key must exist and `m1` and `m2` must equal Ganjoor's text after normalising (diacritics, punctuation, half-spaces, digits, Arabic letter forms), else 400 `bad_couplet`; the stored text is Ganjoor's. A move is +1 for the player; 20 moves a minute per user (429 `rate_limited`). `POST /v1/games/{id}/resign` («کم آوردم», active games only, also out of turn) ends it with the other as winner. Overdue games are also ended when read (`GET /v1/games/{id}`, `/v1/me/games`) and by a sweep every 30 seconds (`src/games.ts`, started in `src/server.ts`); the same sweep ends a duel that nobody runs (one that was on when the server restarted), ends waiting games older than 7 days (done, `end_reason` `expired`, not joinable any more) and deletes expired challenges. League points when a game ends: 10 per accepted couplet up to 400 (`mosh`), 30 per round won up to 150 (`duel`), recorded once, in the Tehran week of the end; `POST /v1/scores` does not take these two games.

**Verification fetch.** `src/ganjoor.ts` reads `https://raw.githubusercontent.com/ganjoor/ganjoor-data/<sha>/poets<path>.json` (for example `…/poets/hafez/ghazal/sh3.json`), where `<sha>` is `source.sha` of the app's `poets.json`, and groups `Verses` into couplets exactly as `tools/ganjoor/couplets.py` does (drop `Comment`; `Right` and the others go in `m1`, `Left` and `CenteredVerse2` in `m2`; a new couplet when the `CoupletIndex` changes or a half would repeat), so the index of a key is the phone's. Poems are kept in memory, the last 500 used; a fetch has a 5 second timeout; a poem that does not exist is 400 `bad_couplet`; at most 60 poems a minute are fetched for the whole server (a poem already in memory costs nothing), past that 503 `busy`; GitHub being down, slow or answering something else is 503 `unavailable`. Tests give `Deps.fetch` a stub.

**Game data.** The deck of well-known couplets (`games.json`), the poets and curated books for the questions (`library.json`) and the pinned commit (`poets.json`) are the app's own files. The Dockerfile copies the three into `apps/server/data` and `.railway/railway.ts` watches them, so a new deck redeploys the server; without that folder (local runs, tests) `src/gameData.ts` reads them from `apps/ios/Yebeyt/Resources/Data`.

**بازی رودررو (live).** When a duel is active and both players have an authenticated socket, the server starts it. If one is not online the game waits for them; if they have not come after 15 seconds the other wins. Five rounds, run by `src/duel.ts` with timers in memory (one server instance only, like the hub). Questions come from `src/quiz.ts`, which mirrors the iOS `QuizMaker`: five different deck couplets, each of a random type: `second` (مصراع دوم: the right second hemistich and two of the same poet's, the same ending first), `poet` (حدس شاعر: the poet and three others, the same century first) or `book` (از کدوم کتاب؟: the couplet's curated book and up to two other books of the poet). The generator is the phone's `SeededGenerator`, seeded randomly (tests fix the seed). Events to both players:

- `{type:"game.started", game}`: the second player joined (any game kind).
- `{type:"duel.question", gameId, round (1 to 5), rounds: 5, kind: "second"|"poet"|"book", couplet: {m1, m2?}, poet: name|null, options: [text], deadlineMs: 8000}`: sent 3 seconds after the start, then 2.5 seconds after each round's result. (`kind`, not `type`, because the event's own `type` is taken.) `couplet.m2` is left out for `second` (it is the answer); `poet` is the poet's name for `second` and `book`, null for `poet`. A player who reconnects during a round gets the question again with the time left in `deadlineMs`.
- `{type:"duel.answered", gameId, round, username}`: that player answered wrong and is locked out of the round (the right answer is never sent before the round's result).
- `{type:"duel.round", gameId, round, winner: username|null, rightOption: index, scores: [{username, score}]}`: the first right answer wins the round at once; the round also ends, with no winner, when both are locked out or the 8 seconds run out.
- `{type:"game.ended", gameId, winner: username|null, reason, scores, couplets?}`: after round 5 (`reason` `finished`); more rounds won wins, equal scores are no winner. Also sent for `timeout`, `resigned` and `left`. A duel that has played rounds carries `couplets` whichever way it ends: the rounds played so far as `{round, type, key, m1, m2, meaning, poet, bookTitle, winner}`; the same data is in `GET /v1/games/{id}` as `rounds` once the game is done.

The client sends `{"type":"duel.answer","gameId":"<uuid>","round":1,"option":2}` (`option` is the index in `options`). Messages are validated with zod; one that is not valid, a late or repeated answer, one for another round or game, or one from someone not in the duel is ignored, and a socket may send at most 10 messages a second (the rest are dropped). A player with no authenticated socket for more than 15 seconds loses: the other wins (nobody does if both are away). Giving up (`POST /v1/games/{id}/resign`) ends it at once.

Other game events: `{type:"game.move", gameId, move: {n, username, key, m1, m2, createdAt}, scores}` and `{type:"game.turn", gameId, username, deadline}` after a مشاعره move; `{type:"challenge.result", code, game, result: {name, username|null, score, seconds}}` to the maker of a challenge when someone leaves a result.

**Public lookups.** `GET /v1/public/users/{username}` and `GET /v1/public/games/{code}` need no account and feed the link pages `yebeyt.com/i/<username>` and `/g/<code>`: `{username, displayName, avatar}`, and `{kind, creator: {username, displayName, avatar}, status: "waiting"}` for a game that still waits for its second player (any other game, or an unknown code, is 404). Both share one bucket of 1200 a minute for the whole server (the web pages cache a good answer for 60 seconds) (429 `rate_limited`).

**Challenges.** جورچین and حدس شاعر with a friend: the same ten couplets and the scores side by side. `POST /v1/challenges {game: "jigsaw"|"poet", items: [10 different keys of couplets in the game deck], score 0–10, seconds ≤ 3600}` gives `{code, url: "https://yebeyt.com/c/<code>"}` (four-character code, valid 30 days, 30 an hour per user). `GET /v1/challenges/{code}` needs no account (all lookups together share 600 a minute): `{creator: {username, displayName, avatar}, game, items, score, seconds, label}`, where `label` («۱۰ بیت سعدی») is made when all ten couplets are by one poet (the poet is the deck's, named from the app's poet list) and is null otherwise; an expired or unknown code is 404. `POST /v1/challenges/{code}/results {score, seconds, name?}`, signed in or not: without an account `name` is required (1 to 30 characters, no control characters); with one the result is theirs, one per person, and not for the maker (409 `conflict`). Guests share 120 results an hour; a signed-in user has 60. The maker gets a live `challenge.result` and, when the player has an account too and nobody blocked the other, a chat message of kind `game` (sent by the player, so it counts as unread) with `{event: "challenge_result", code, game, score, seconds}`. `GET /v1/me/challenges` lists mine that have not expired with their results (best score first, then fastest; people who blocked or were blocked are left out). Expired challenges and their results are deleted by the sweep.

## The contract

`packages/api/openapi.json` is generated by `scripts/openapi.ts` from the route definitions; never edit it by hand. After changing a route, run `api:generate` and commit it. `api:check` (and a test) fail when it is out of date.

## Poet pictures

Stored in Postgres (`poet_pictures`), served with `ETag` and a day of caching. Upload from `design/poets` (white lines on transparent; made from round2 with to_white.py):

```bash
API_URL=http://localhost:8080 ADMIN_TOKEN=… pnpm --filter @yebeyt/server pictures:upload design/poets
pnpm --filter @yebeyt/server pictures:upload design/poets --dry-run   # resize only, upload nothing
```

The script takes `poet-<name>.png`, maps the name to the Ganjoor slug (`rumi`→`moulavi`, `ferdowsi`→`ferdousi`, `rudaki`→`roodaki`, the rest are the same), checks the slug against `apps/ios/Yebeyt/Resources/Data/poets.json`, resizes to 512×512 WebP quality 82 (WebP keeps the transparent background) and uploads. Files whose poet is not in `poets.json` (today akhavan, forough, nima, shamlou, sohrab) are skipped and listed.

## Deploy (Railway)

The Dockerfile builds from the **repo root** (it needs the lockfile and the workspace files):

The Railway project (services, the Postgres, builds, health check, the custom domain) is described in `.railway/railway.ts` at the repo root. The `server` service is connected to this repo: every push to `main` that touches the server, `packages/`, the workspace files or the game data files (`games.json`, `library.json`, `poets.json`) builds `apps/server/Dockerfile` and deploys it, with `/health` as the health check. Environment variables are not in the file (`variables: { managed: false }`); they live only in Railway.

- Preview a change to the infrastructure: `railway config plan` (from the repo root, after `railway link`). Apply it: `railway config apply`.
- A manual deploy of the working tree: `railway up --service server` from the repo root.
- api.yebeyt.com is a custom domain on the service; Cloudflare holds the CNAME.

The image also holds `data/` (the game deck, the library and the pinned commit, copied from `apps/ios/Yebeyt/Resources/Data`; `Dockerfile.dockerignore` lets those three files through). Local image check, if Docker is available: `docker build -f apps/server/Dockerfile -t yebeyt-server .`
