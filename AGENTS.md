# yebeyt · agent guide

This file is the one source of rules for every coding agent on this repo: Claude Code, Codex and GitHub Copilot. `CLAUDE.md` and `.github/copilot-instructions.md` only point here.

yebeyt («یه بیت») is a Persian poetry app with games, friends and messages, in a sticker style. It is being built **from scratch** as a monorepo: iOS first, then the server, the website and links; a web app, an admin dashboard and Android come later. No earlier code or user data is carried over (the old 1.0 app was never distributed; it lives only in git history, `main` before the foundations slice). The design and every product decision are in [docs/yebeyt-2.md](docs/yebeyt-2.md). Read that before planning any work. What only the owner can do (DNS, cloud consoles, device tests) is listed in [docs/owner-todo.md](docs/owner-todo.md).

What the browser keeps (follows, reading progress, rejected couplets, marks) is in localStorage under the phone's names and JSON. `app/api/[...path]` is the web app's own door to the server (no CORS, and the session): only the paths and methods of `lib/api/proxy.ts` go through (the poet pictures, the username check, `PUT /v1/me/username|profile|progress`, the divan, the reactions, `POST /v1/scores|daily`, `GET /v1/me/stats`, `PUT /v1/me/avatar`, `GET|PUT /v1/me/privacy`, `DELETE /v1/me`, and for friends (W6) `GET /v1/users/search|<username>`, `POST|DELETE /v1/friend-requests/<username>`, `POST` its `/accept` and `/reject`, `DELETE /v1/friends/<username>`, `GET /v1/me/friends|friend-requests|unread`, `PUT /v1/blocks/<username>`, `POST /v1/reports`, `GET /v1/leaderboard/league|friends|global`, `GET /v1/feed` and `GET /v1/reactions/counts`; a username in a path starts with a letter and has letters, digits, «_» and «.»; and for messages (W7) `GET|POST /v1/conversations`, `GET|POST /v1/conversations/<id>/messages`, `PUT` its `/read`, `DELETE /v1/messages/<id>`, `GET|POST /v1/shared-divans`, `GET|POST /v1/shared-divans/<id>/items`, `DELETE` an item and `PUT|DELETE` its `/like`; an id is letters, digits, «_» and «-»; and for games with friends (W8) `POST /v1/games`, `GET /v1/games/<id>`, `POST` its `/join|moves|resign`, `GET /v1/me/games`, `POST /v1/challenges`, and `GET /v1/challenges/<code>` and `POST` its `/results`, which go with the session when there is one and without it for a guest (a code is four letters or digits; not joining by code, not `/v1/me/challenges`)), it asks `API_URL` (default the Railway URL, as `apps/web`), and a write needs the page's own origin (`Sec-Fetch-Site` or `Origin`). The session is two httpOnly, SameSite=Lax cookies (`yb_access`, `yb_refresh`; `Secure` when the page is served over https), which only the web app's own server reads: it sends the access one as a Bearer token, refreshes on a 401 once (one refresh for the requests that meet it together) and clears both when the server refuses the refresh token; no page script ever sees a token. `app/auth/apple|google` take the provider's token (Sign in with Apple JS in a popup, its nonce hashed for Apple and raw for the server; Google Identity Services' id token), `app/auth/session` says who is signed in and `app/auth/logout` ends it; they answer with the user only. `POST app/auth/live` (same origin only, `Cache-Control: no-store`) is the one place a token reaches page script: it gives a fresh access token (the cookie's while it has a minute left, else the session is refreshed first and the cookies set) and the address of the live socket made from `API_URL` (`wss://<API host>/v1/live`), which the page sends as the socket's first message. The types of the contract are `lib/api/schema.d.ts` (`pnpm --filter @yebeyt/webapp api:types`; a test fails when it is out of date). Env: `API_URL`; the public ids `NEXT_PUBLIC_APPLE_SERVICES_ID` (`com.yebeyt.web`) and `NEXT_PUBLIC_GOOGLE_CLIENT_ID`, read when the page is built (the Dockerfile passes them on), without which the sign-in buttons stay off with «ورود روی وب به‌زودی»; the return URL of Apple is `<origin>/auth/apple` (`https://app.yebeyt.com/auth/apple`), which the server must list in its `APPLE_REDIRECT_URIS` (and the Services ID in `APPLE_BUNDLE_IDS`, the web client id in `GOOGLE_CLIENT_IDS`). The account (gate, username step, sync) is `lib/account/` and `components/account/`: the divan, the likes and reposts and the scores sync as on the phone (`DivanSync`, `ReactionsSync`, `ScoreSync`; on sign-in, when the page comes to the front or back online, after a change; what could not be sent waits in localStorage under `reader.reactions.unsent` and `scores.unsent`), guest points go to the account on the first sign-in (`PUT /v1/me/progress`), and the sign-out (in `/me/settings`) warns when something did not reach the account. Me (W5) is the من tab: `/me` (the profile: face, name, level/points/streak, badges, the divan's first couplets, «+ دوستاتو بیار», the gear), `/me/divan` (the kept couplets by poet, topic or newest, with search, poet chips, «برگردون» and the day on each card), `/me/avatar` (the editor; a guest's face stays in `me.avatar`, a signed-in person's goes to `PUT /v1/me/avatar`, an unsent one stays marked in `me.avatar.unsent`), `/me/invite` (the link `yebeyt.com/i/<username>`, the tones, the text by hand, the messengers, «استوری» as a 1080×1920 PNG drawn on a canvas, copy; a guest gets the gate), `/me/settings` (name, username, sign out with the unsynced warning, delete account, text sheet, privacy, terms, feedback («به‌زودی» until W9), licences; left out because they make no sense in a browser: the shake for feedback and the version line), `/me/privacy` (`me.privacy` and `me.privacy.unsent`, sent as partial updates to `PUT /v1/me/privacy`), `/me/badges` and `/me/licenses`; `/me/blocked` does not exist because the phone has no screen for blocked people. The code is `lib/me/` (logic and stores, with Vitest ports of the phone's tests) and `components/me/`; the tab bar's من shows the person's face. The face is drawn by the workspace package `packages/avatar` (`@yebeyt/avatar`: the parts, their colours and `AvatarFace`, which `apps/web` uses too; a test there holds the parts to `AvatarParts.swift`). Signing out and deleting the account forget the account's data in the browser (`lib/account/signOut.ts`, `deleteAccount.ts`: the divan, likes, privacy settings, face and what is unsent); `DELETE /v1/me` goes through the door only for that. In a debug build `sessionStorage.beytSeedDivan = "1"` keeps 20 sample couplets on different days (the phone's `-beytSeedDivan 1`). Onboarding (`components/onboarding/`) is in front of the home on the first visit to `/` and never again (`onboarding.done`); its taste is `taste.poets`/`taste.moods`, and the home picks today's couplet from those poets. In a dev build or one *built* with `NEXT_PUBLIC_DEV_PAGES=1` only (the value is baked in when the app is built, for the server's code too: setting it on a running server changes nothing, so Railway must not set it at build either): `sessionStorage.beytOnboarding = "welcome|taste|game|account|username|friends"` starts onboarding there (the phone's `-beytOnboarding`; a debug build shows none without it), `first` makes it behave as a release build, and while the gate or the account step is open `window.beytSignIn({ id?, username?, providerName?, provider?, syncFails? })` signs in as if a provider had answered (the phone's `-beytSignedIn 1`): the door answers such a session itself from a stub server (`lib/api/stub.ts`: `username: null` is a new account, `syncFails` makes it refuse the divan for the sign-out warning, `sara`, `aryan`, `hafez` and `niloofar` are taken names). The stub also keeps the avatar and the privacy settings and forgets a deleted account (`DELETE /v1/me`). In a dev build, or one made with `NEXT_PUBLIC_DEV_PAGES=1`, `sessionStorage.beytToday = "yyyy-mm-dd"` fixes the day the home couplet and the date line go by, at noon on the device's clock (the phone's `-beytToday`); it also fixes the Tehran day of the games, at noon there, and `sessionStorage.beytSeed = "<n>"` fixes the جورچین round (the phone's `-beytPlay` has no twin yet). Friends (W6, `lib/friends/` and `components/friends/`, the phone's `Friends/`): `/people?q=` is «پیدا کردن دوست» (the search waits 300 ms and wants two characters, as on the phone), `/u/<username>` is a person's page (the friend button in every state, `قبول` with `رد`, the ⋯ menu with «حذف از دوستا», «بلاک» and «گزارش», each asking as on the phone; yebeyt.com's `/i/<username>` has «روی وب باز کن» to it), `/messages/requests` is «درخواست‌های دوستی» (the «درخواست‌های دوستی» row with its count shows at the top of پیام‌ها, and the tab bar's badge counts the requests with the unread messages), `/me/friends` is «دوستا» (the profile's «<n> دوست» opens it), the home has «دوستات» for a signed-in person (the feed with the counts of reactions; a guest sees nothing), and `/games/leaderboard?tab=league|friends|global` is رده‌بندی (the بازی tab's points open it; the tabs slide and never fade). Every action asks for an account (the gate says «پیام دادن به دوستات», or «دیدن رده‌بندی» for the board) and goes ahead after the sign-in; blocking hides the person from the lists loaded and from what the server sends next (`BlockedPeople`, in memory, by account). The debug server (`lib/api/stubFriends.ts`) has the phone's demo people: سارا, کیان and مهسا and «یه بیت» (`canPlay: false`) are friends, آرین and بردیا asked, پریا was asked, رها has nothing, for each debug account on its own. «پیام بده» (when the profile says `canMessage`) opens the chat. Messages (W7, `lib/messages/` and `components/messages/`, the phone's `Messages/`): `/messages` is پیام‌ها (the chats newest first with a search, the «درخواست‌های دوستی» row, «بازی با دوست» (the lobby, W8) and the pencil, which opens «پیام تازه»; a guest gets the gate), `/messages/<username>` is the chat (text bubbles, couplet cards that open the reader at the couplet, «دیده شد», game lines and cards (W8: the مشاعره card of the board, an invitation with «بزن بریم» or «ببین», a line for a game that ended or a challenge's result; the buttons open the game, joining it first), the quick actions (the two games open the lobby with that game and this friend chosen, «معمای امروز» opens the puzzle; «یه بیت» has no game chips; a challenge link in a text opens its board), the composer (Enter sends, Escape and a tap on the messages put the keyboard away), the couplet picker «بیت بفرست», retry of a send that failed, older messages when the list is scrolled to its top, a long press, right click or the menu key on a message asks to delete mine or to report theirs), `/messages/<username>/divan` is دیوان من و <name> (chips, likes, `+` with the picker, a long press or right click on a couplet I added asks «از دیوان مشترک برداشته بشه؟») and the reader's hold menu «به دیوان مشترک» opens the sheet to choose a friend (`MessagesCenter.askSharedDivan`). The chat, the shared divan and the requests are drawn without the tab bar on a phone (as on the phone); from 1024 px the inbox stays beside the open chat (two panes; the library's list and detail side by side was not built). The unread number of the tab badge is `FriendsCenter.unreadMessages` (the server's, plus live messages that count while their chat is not open). One socket per tab (`MessagesHost` in `AccountRuntime`): `lib/messages/liveConnection.ts` sends `{type:"auth",token}` as its first message, handles `ready`, the events (`message`, `read`, `deleted`, `presence`, `divan`, `divan.removed`, `friend.request`, `friend.accepted`; the games' go to `FriendGames` (W8), which reads `/v1/me/games` and the open games again on every connect; `LiveConnection.send` sends a text frame once the server said ready and never one over its 4 KB), the close codes (4401 asks for a new token at once, 4403 stops, 4409 stops until the page comes back) and reconnects with 1, 2, 4 … 30 s; it is closed when the page has been hidden for a minute and on sign-out, and every connect reads the lists on screen again. A browser cannot send a ping: the server's are answered by the browser. Every view of message text or typed text carries `data-feedback-private` (`lib/feedbackPrivate.ts`, for W9's screenshot). In a dev build or one built with `NEXT_PUBLIC_DEV_PAGES=1`: the debug server (`lib/api/stubMessages.ts`, the phone's `Debug/MessagesBackend.swift`) has the five chats, Sara's divan of 24 couplets and Kian's, and `chat/yebeyt`; it remembers what is sent, read, added, taken out and liked, and `sessionStorage.beytLive = "1"` makes the page's socket a fake one that brings a message from Sara after 1.5 s (the phone's `-beytLive 1`); `sessionStorage.beytDivanSheet = "1"` opens the sheet of «به دیوان مشترک» for a Hafez couplet once signed in (the phone's `-beytDivanSheet 1`; the reader's hold menu shows it too: `/poem/hafez/ghazal/sh3?c=1`, right click the couplet). The بازی tab is `/games` (streak, points, today's puzzle, four game cards) and `/games/catalog` is the grid of all nine; a game opens over the tabs as one cover that rises like the reader: `/games/daily` (معمای امروز) and `/games/jigsaw` (جورچین بیت), in the parallel slot `@game` of `app/(shell)` beside `@reader` (opened by its link, the game is the page's own layer, so the reader opens over it the same way); `/games/jigsaw?poem=<path>&c=<n>` starts with that couplet (the reader's «بازی با این بیت», `c` left out for «بازی با این غزل»; over a round that has started it asks «از بازی بری بیرون؟» first). The solo quiz games open the same way at `/games/poet` (حدس شاعر), `/games/misra` (مصراع دوم; `?poet=<slug>` makes it a round of that poet, which is the poet page's «بازی با بیت‌های …» card), `/games/book` (از کدوم کتاب؟), `/games/match` (معنی‌یاب) and `/games/listen` (گوش کن); `sessionStorage.beytSeed` fixes their rounds too. گوش کن plays the first hemistich of a Hafez couplet from api.ganjoor.net in one `<audio>` (`lib/games/clipPlayer.ts`): nothing plays before the first press of play, the clip ends at the deck's measured `clip` (else the second hemistich's mark − 0.8 s) watched by `timeupdate` and every animation frame, and a Web Audio gain (`webAudioFade.ts`) fades its last 80 ms (measured) or 0.25 s; the games with a friend ask for an account. Scores and the daily puzzle's tries are kept in localStorage `games.stats`, in the phone's `GameStats` JSON (`points`, `solvedDays`, `best`, `daily` by Tehran day number). Playing with friends (W8, `lib/play/` and `components/play/`, the phone's `Play/`; `FriendGames` is `services.games`): `/games/lobby?game=mosh|duel|jigsaw|poet&with=<username>` is «بازی با دوست» (the four games, the turn time for مشاعره, three of my friends who can play (`canPlay`: «یه بیت» is not offered) and «بیشتر», the link made with the game when a way to share it is pressed, «بساز و دعوت کن»: a مشاعره or رودررو is made on the server and replaces the lobby, جورچین and حدس شاعر open `/games/jigsaw|poet?invite=<usernames>` to play first), `/games/mosh/<id>` is مشاعره (the couplets played, the letter, the suggestions from the divan and the bundled books (`MoshSuggestions`), a typed text matched with the books before it is sent, «کم آوردم» asks first, the opponent's move comes live as `game.move` and `game.turn`, the end says who won and why), `/games/duel/<id>` is رودررو (five rounds from `duel.question`, my answer sent as `duel.answer` over the socket, the clock, «جواب داد», `duel.round`, then `game.ended` with the five couplets and their meanings; an answer that cannot be sent is taken back with «جوابت نرسید؛ دوباره بزن», a lost socket comes back by itself and the server asks the open round again; leaving a round that is on asks first), and `/c/<code>` is the board of a challenge (`yebeyt.com/c/<code>` has «روی وب بازی کن» to it): it plays exactly the maker's ten couplets with جورچین or حدس شاعر, and ends by posting the result, with the account when there is one, else after asking «اسمت چیه؟» (a guest needs no account). After a جورچین or حدس شاعر round a signed-in person sees the challenge card instead of the couplets (`POST /v1/challenges`, the link, the ways to share it, «توی اپ: …» sends it to a friend as a chat message). The بازی tab has the مشاعره card (the game where it is my turn first, «با یه دوست») and «+ بازی با دوست»; the catalog's two cards open the lobby. The `@game` slot also holds `(.)games/lobby`, `(.)games/mosh/[id]`, `(.)games/duel/[id]` and `(.)c/[code]`; `GameLayer` is the cover, `GameCover` the solo games' wrapper. In a dev build or one built with `NEXT_PUBLIC_DEV_PAGES=1`: the debug server (`lib/api/stubPlay.ts`, the phone's `Debug/PlayStub.swift`) has `g1` (مشاعره with Sara, my turn, the couplets chain on «س» and «د»; Sara's answer to my move is in the game two seconds later), `d1` (رودررو, round four of five: the tests push the live events), `g2` (the duel Aryan invited me to), games made in the lobby (`new-mosh`, `new-duel`, waiting), and the challenge `7KQ2` (ten couplets by Saadi, 8 of 10 by نیلوفر); `sessionStorage.beytPlayStub = "1"` makes the door answer games and challenges for a visitor with no session (the phone's `-beytPlayStub 1`: a guest opening `/c/7KQ2`). Not built: the picture of «استوری» for a challenge, the scripted live replies of the phone's stub. **Feedback** (W9; `lib/feedback/`, `components/feedback/`, the phone's `Feedback/`): «بازخورد» in the settings and Shift + «?» from anywhere (not while a field has the keys, not over another dialog) open «می‌خوای چیزی بگی؟» with the five types over the page as it was (`FeedbackHost` in the root layout; no shake and no floating button on the web); the forms, copy, limits and the question before an unsent one is closed are the phone's, and a report goes `POST /v1/feedback` (the session when there is one, a guest's without it) then `PUT /v1/feedback/<id>/screenshot|recording` with the upload token, through the door, which lets exactly those through and is the only place that takes a body over 1 MB (3 MB for a screenshot, 25 MB for a recording: `lib/api/proxy.ts`). The screenshot is drawn in the browser by modern-screenshot (`lib/feedback/screenshot.ts`): the copy it draws has every `data-feedback-private` element and every input, textarea, select and editable element turned into a solid block (`lib/feedback/privacy.ts`), never painted over afterwards, so a bug report can't carry typed text or messages; a JPEG of at most 1600 px and 3 MB is sent, after the editor's marks («خط بکش یا بپوشون»). Recording is `getDisplayMedia` and `MediaRecorder` as **MP4, or WebM** where the browser can't do MP4 (the server takes both), of this page only (`displaySurface: "browser"` and no switching; a stream that is not a tab is refused and stopped, and Capture Handle confirms it is this tab where the browser has it, else «فقط همین صفحه رو انتخاب کن»), stopped when the page is hidden or left; a browser that can't share the screen or can't say which surface it captures (iPhone Safari) has no recording option, at most 60 s and 25 MB; while it runs every private view is covered (`lib/feedback/covers.ts`, a block over each, followed every frame, in the top layer so sheets don't hide it) and the red pill «در حال ضبط · تموم» is a popover above the game, the reader and every sheet. The technical info is the screen name, the poem's couplet and mode, the text settings, the connection, signed in or not, the log of the last 20 screens and error codes (`FeedbackLog`, in memory, never text), and the build's git sha, the browser with its window size and language, and the system go in the report's version, model and system fields. Dev hook (a dev build or one built with `NEXT_PUBLIC_DEV_PAGES=1`): `sessionStorage.beytFakeRecorder = "1"` stands a fake recorder in for the browser's (the phone's `-beytFakeRecorder 1`: the record button starts at once, «تموم» keeps a tiny MP4); the tests answer the door's feedback calls themselves (`e2e/feedback.ts`: offline, 429, busy, too big, as `-beytFeedbackFails`). ## Build and check

- iOS (needs a Mac with Xcode 26 or later and `brew install xcodegen`):
  ```bash
  cd apps/ios && xcodegen generate
  xcodebuild test -project Yebeyt.xcodeproj -scheme Yebeyt -destination 'platform=iOS Simulator,name=iPhone 17'
  ```
  Use any simulator from `xcrun simctl list devices available`. Agents make their own private simulator (`xcrun simctl create yb-<task> "iPhone 17"`, plus an iPhone SE for small screens), delete it afterwards, and never run `simctl shutdown all`, because a shared simulator gives false failures when several agents work at once.
- TestFlight: `tools/testflight.sh` archives `main` and uploads it (Xcode must be signed in to team 95YDC2AP63; the build number is the date and time). It refuses a dirty tree or a HEAD other than the latest `origin/main` unless `--force` is passed. Builds appear in App Store Connect → TestFlight after processing; add them to the «K&S Team» group.
- Tokens: after editing `packages/tokens/tokens.json`, run `python3 tools/make_tokens.py`; `python3 tools/make_tokens.py --check` fails when a generated file is out of date. Never edit generated token files by hand.

## Rules

Product:
- Everything the user sees is Persian and right-to-left. Use the everyday Persian word wherever one exists (رده‌بندی, not لیدربورد; پیام‌ها, not دایرکت).
- The app works **without an account**: reading, library, search, fal, listening, solo games, the divan on the phone. Only features with a server behind them (scores, leaderboard, streak, playing with friends, messages, sync) ask for an account, at the moment they are used, never up front.
- Sign-in is **only Apple and Google**. No email or phone sign-up.
- No religious symbols anywhere in icons or art (no crescent, star, mosque shapes, calligraphy of holy names).
- Feedback reports follow the privacy rules in `docs/yebeyt-2.md`. Never send typed text from elsewhere, messages, phone number, IP or location. Any view that shows typed text or message text carries `.feedbackPrivate()`: it is blanked in feedback screenshots and covered while a recording runs.

Code and data:
- Keep files small and simple. No dead code, no speculative abstractions. Handle errors at the boundaries.
- Never commit secrets: `apps/ios/Config/Local.xcconfig`, `.p8` keys, tokens, `.env` files. Never commit user data or Ganjoor reader comments.
- Poetry data comes from Ganjoor's public repositories (github.com/ganjoor). Fonts and poetry data keep their own licences; add any new font to `assets/fonts/` with its licence in `assets/fonts/licenses/` and a row in `THIRD_PARTY_NOTICES.md`.
- Host every service on Railway (server, web, admin, databases).

Git:
- Commit with the GitHub no-reply address. On a new machine, once: `git config user.email 5063636+thekeyvan@users.noreply.github.com`.
- Never commit straight to `main`. One branch per slice (`feat/<slice>`, `fix/<what>`), short imperative commit subjects like the existing history.
- Merge into `main` (fast-forward), push and delete the branch **only when the user says so**.

## How we work: three tiers

Every tool runs the same three roles, each pinned to a model tier. The person's main conversation is the **lead**.

| Tier | Role | Does |
|---|---|---|
| High | **lead** (main conversation) | Plans, writes briefs, design and product decisions, research, debugging analysis, docs, talks to the user. Does not write product code |
| High | **reviewer** | Every code review. The only one who may call a review clean. Never edits |
| Mid | **builder** | All code: tests first, then the change, then the fix rounds after a review |
| Small | **mechanic** | Build and CI logs, simple union merge conflicts, status and doc edits, waiting on checks |

The loop for each slice:

1. **lead** picks the next slice (see the order in `docs/yebeyt-2.md`, and confirm it with the user), creates the branch, and writes the builder a brief: the screens (by board file in `design/canvas/project/`), the files to touch, the behaviour, acceptance criteria, and how to build and test.
2. **builder** builds it test-first on that branch, runs the checks, commits, and reports.
3. **reviewer** reviews the branch against the brief and these rules, and lists findings as `must-fix`, `should-fix` or `judgement`.
4. **builder** fixes exactly those findings. At most two fix rounds, then one review-only round. Only the reviewer says `clean on <sha>`.
5. **lead** tells the user what landed, shows proof (test output, simulator screenshots), and merges and pushes only on the user's word.

Small non-code edits (docs, notes, config text) can stay with the lead.

Where each tool keeps the roles. All of these files are written by `tools/make_agent_roles.py` from one text: change a role there and run `python3 tools/make_agent_roles.py`, never edit the copies by hand.

| Tool | Role files | Lead |
|---|---|---|
| Claude Code | `.claude/agents/{builder,reviewer,mechanic}.md` (models by alias: `opus`, `sonnet`, `haiku`) | the main conversation, on `opus` (`.claude/settings.json`) |
| Codex | `.codex/agents/{builder,reviewer,mechanic}.toml` | the main session, model set in `.codex/config.toml` (the project must be trusted for Codex to read `.codex/`) |
| GitHub Copilot | `.github/agents/{lead,builder,reviewer,mechanic}.agent.md` | pick the **lead** agent in the chat's agent picker; it calls the other three as subagents |

Codex and Copilot have no model aliases, so their files name versioned models. When a newer model ships, update the model lines in those files.
